# 自写文档记忆：模型自己写一份限长文档，再只凭它答题

日期：2026-10-14 · 分支：`master`（工作区，未提交）· 运行：北京时间 11:12–12:12，DeepSeek 高峰时段 · 花费约 113 元（按高峰价从用量估算，以 DeepSeek 后台为准）

## 结论

1. **纯文档模式没有带来更好的 LoCoMo / LongMemEval-S 指标。** 准确率随文档预算单调上升，但在所有测过的预算下都低于把原文整段放入：
   - LoCoMo（1540 题）：4 / 8 / 16 / 32 KiB 依次为 52.0% → 59.7% → 73.3% → 83.1%，原文 92.4%。
   - LongMemEval-S（60 题）：61.7% → 61.7% → 68.3% → 86.7%，原文 93.3%。
   - 32 KiB 档仍比原文低 9.4 分（LoCoMo，p < 1e-28）和 6.7 分（LongMemEval-S，区间跨 0）。
2. **这是文档模式的上限。** 写入者一次读完整份历史，知道每件事最后的状态，也能全局分配篇幅。线上的 runtime memory 是边聊边记，只会更差，所以上面的负面结论不依赖增量写入的实验。
3. **曲线在 LoCoMo 上每档都显著，到原文之前没有出现平台。** 相邻两档的配对差为 +7.7、+13.6、+9.7 分，McNemar 检验 p 均 < 1e-10；10 段对话各自的曲线形状一致。LongMemEval-S 在 4–16 KiB 平缓，16→32 KiB 跳升 18.3 分（p = 0.003）。
4. **丢掉的是细节和日期，保住的是概括。**
   - LoCoMo：多跳题在 4 KiB 就有 77.7%（原文 93.6%）；单跳题只有 46.3%（原文 95.5%），时间题 46.4%（原文 91.6%）。
   - LongMemEval-S："单会话·助手"类最差，4 KiB 只有 20%（原文 100%）；助手给出的具体内容最先被舍弃。
5. **模型不愿意写满大预算，写多长也不稳定。**
   - 16 KiB 档平均只用了 62–71%，32 KiB 档 59–73%，64 KiB 档 44–54%。
   - 把预算从 32 KiB 加到 64 KiB，LoCoMo 没有提高（82.5% 对 83.1%），同一段对话的文档甚至可能更短。
   - 就算几乎不压缩也有损失：3 段对话的 64 KiB 文档达到原文的 58–71%，准确率仍比原文低 2.4–4.2 分。改写本身就丢信息。
6. **在相近的读入量下明显落后于 Mnemon。** 16 KiB 档每题读入约 2.6k–3.0k token，LoCoMo 73.3%；32 KiB 档读入 5.7k token，也只有 83.1%。Mnemon 每题给作答模型约 3.8k token（论文的标准设置），用 DeepSeek 作 System 2 时 LoCoMo 为 92.2%。两者不是逐题配对，但差距远大于运行之间的差异。
7. **对产品的含义。** runtime memory 默认上限（MEMORY 10 KiB + USER 4 KiB）接近这里的 16 KiB 档，对应 LoCoMo 约 73%、LongMemEval-S 约 68%。自写文档适合作为原始记录之上的概览层，不适合替代原始记录来承担长期召回。

## 1. 实验设计

### 1.1 数据

| 数据集 | 规模 | 每份记忆 |
|---|---|---|
| LoCoMo | 10 段对话，1540 题（不含对抗类），原始标签 | 52–106 KB，约 1.3–2.5 万 token |
| LongMemEval-S（清洗版） | 60 题：6 种题型各 10 题，按题目 id 的哈希固定抽取（`stratified()`，与仓库此前的历史放大实验同一批），含 3 道拒答题 | 约 50 万字节，约 10.5 万 token |

数据文件 sha256：`locomo10.json` 为 `79fa87e9…98ff4`，`longmemeval_s_cleaned.json` 为 `d6f21ea9…c3a442`。

### 1.2 组别

| 组 | 写入 | 作答时看到 |
|---|---|---|
| 原文整段放入 | 无 | 全部原文（与 run.ts 的 `full-context` 组相同） |
| `doc:<KiB>` | ds flash 读完整份历史，写一份不超过 `<KiB>` KiB（UTF-8 字节）的文档 | 只有这份文档 |

- **写入提示**（`doc-writer/v1`）：告诉模型历史随后会被删除，以后要凭这份文档回答关于这些对话的问题，读者看不到原文和日期，问什么不知道；文档怎么组织由模型自己决定；只写历史支持的内容。写入者看不到任何题目。
- **预算放在提示最后**，同一份记忆的各档共享原文前缀，后几档的原文部分命中 DeepSeek 缓存。
- **超预算处理**：把超出的字节数告诉模型让它重写，最多两次；仍超就截到预算内最后一个完整行，并标记为截断。
- **作答提示**与 run.ts 逐字相同，只把"对话历史"换成"记忆文档"。

### 1.3 模型与判分

- 写入：`deepseek-flash`，开思考，reasoning_effort high，输出上限 32768（64 KiB 档为 49152）。
- 作答：`deepseek-flash`，开思考，reasoning_effort high，输出上限 8192。
- 判分：`judge.ts` 默认的 DeepSeek 评分（LoCoMo 用 Mem0 的宽松 CORRECT/WRONG；LongMemEval-S 用其分题型的 yes/no 判定）。
- 区间：按记忆重采样的 bootstrap（10,000 次，固定种子；LoCoMo 以对话为单位，LongMemEval-S 以题目为单位）。配对差用同样的 bootstrap，显著性用 McNemar 精确检验。

### 1.4 32 KiB 档的取值规则

32 KiB 档在两个数据集上各有两次测量：32 KiB 预算那次，以及 64 KiB 预算那次（模型写不满，大多数文档落在 32 KiB 附近）。按事先约定取两次中较高者：

| 数据集 | 32 KiB 预算那次 | 64 KiB 预算那次 | 采用 |
|---|---:|---:|---|
| LoCoMo | **83.1%**（文档平均 23.9 KB） | 82.5%（35.3 KB） | 32 KiB 那次 |
| LongMemEval-S | 81.7%（19.4 KB） | **86.7%**（29.0 KB，60 份中 18 份超过 32 KiB） | 64 KiB 那次 |

取较高者有乐观偏差，对 LongMemEval-S 尤其如此，所以 32 KiB 档应读作"这一水平文档模式能达到的较好结果"。

### 2.2 LongMemEval-S（60 题）

| 档 | 准确率 [95% 区间] | 比上一档 | 文档实际大小 | 作答读入 | 每题作答费用 |
|---|---:|---:|---:|---:|---:|
| 4 KiB | 61.7% [48.3, 73.3] | — | 3.7 KB | 1,123 token | $0.00035 |
| 8 KiB | 61.7% [50.0, 73.3] | +0.0 [−13.3, +13.3] | 6.8 KB | 1,837 | $0.00043 |
| 16 KiB | 68.3% [56.7, 80.0] | +6.7 [−6.7, +20.0] | 11.6 KB | 2,976 | $0.00064 |
| 32 KiB* | 86.7% [78.3, 95.0] | +18.3 [+8.3, +30.0] | 29.0 KB | 7,109 | $0.00121 |
| 原文 | 93.3% [86.7, 98.3] | +6.7 [−1.7, +16.7] | 约 500 KB | 105,228 | $0.01608 |

\* 取自 64 KiB 预算那次（见 1.4）；32 KiB 预算那次为 81.7%。

- 原文组与此前在同一批 60 题上的结果一致（历史放大实验 1 倍长度时为 95.0%）。
- 这里每份历史只问一题，原文组每题要读约 10.5 万 token、几乎不命中缓存，所以文档组每题作答便宜 13–46 倍，代价是低 7–32 分。
- 同样大小的文档，LongMemEval-S 的准确率不低于 LoCoMo（4 KiB 档 61.7% 对 52.0%），尽管它要压缩约 90 倍、LoCoMo 只要压缩约 20 倍。LongMemEval-S 的历史大多是与用户无关的对话，值得记的事实少。决定准确率的更像是文档大小与"可能被问到的事实"数量之比，而不是压缩比。
- 60 题只够看曲线形状：低端相邻两档的差别不显著。

## 4. 写入行为

| 档 | LoCoMo 用满预算 | LoCoMo 重写 / 截断 | LongMemEval-S 用满预算 | LongMemEval-S 重写 / 截断 |
|---|---:|---:|---:|---:|
| 4 KiB | 83%（最低 68%） | 1/10 · 0 | 90%（最低 71%） | 27/60 · 0 |
| 8 KiB | 85%（最低 70%） | 0/10 · 0 | 83%（最低 61%） | 15/60 · 1 |
| 16 KiB | 62%（最低 35%） | 1/10 · 0 | 71%（最低 45%） | 4/60 · 1 |
| 32 KiB | 73%（最低 53%） | 0/10 · 0 | 59%（最低 24%） | 4/60 · 0 |
| 64 KiB | 54%（最低 23%） | 0/10 · 0 | 44%（最低 16%） | 1/60 · 0 |

- 小预算下模型经常写超，需要重写；大预算下又写不满。提示里写了"Use the space well"，没有改变这一点。
- 每次写入的思考约 0.6–1.9 万 token；64 KiB 档的总输出接近 3.2 万，所以把上限调到了 49152。
- 写多长不随预算单调：conv-42 的 64 KiB 文档只有原文的 18%，比它的 32 KiB 文档（33%）还短，准确率从 84.4% 掉到 63.8%。单份文档的写入差异很大，这次每份只写了一次，没有测量这种差异。

## 6. 局限

- 32 KiB 档按约定取两次测量中较高者，有乐观偏差（见 1.4）。
- 只用了一个评分模型（DeepSeek）；LoCoMo 用原始标签，按此前报告，修订标签会让各组普遍高 2.6–3.2 分，组间差距不变。
- 只用了一种写入提示，每份文档只写了一次；写入的随机差异没有测量。
- 写入和作答是同一个模型（ds flash）；换更强的写入模型可能抬高曲线，但不改变"写入时压缩丢细节"这一机制。
- LongMemEval-S 只有 60 题。
- 与 Mnemon 的对比不是逐题配对：Mnemon 的数字来自论文，在另一个提交上运行，LongMemEval-S 是全部 500 题。

## 7. 复现

运行记录（作答、判分、全部文档）在 `out/doc-exp/locomo/` 与 `out/doc-exp/lme/`，未收入仓库。密钥放在 `.env`（已被 git 忽略）。

```sh
node --env-file=.env --experimental-transform-types scripts/bench/doc.ts --dataset locomo \
  --arms full-context,doc:4,doc:8,doc:16,doc:32 --concurrency 16 --write-concurrency 9 --max-cny 40 --out <runs>/locomo
node --env-file=.env --experimental-transform-types scripts/bench/doc.ts --dataset longmemeval --per-type 10 \
  --arms full-context,doc:4,doc:8,doc:16,doc:32 --concurrency 12 --write-concurrency 12 --max-cny 53 --out <runs>/lme
# 64 KiB 档（两个数据集各一次，再加 --write-max-tokens 49152）
node --env-file=.env --experimental-transform-types scripts/bench/doc.ts --dataset locomo --arms doc:64 --write-max-tokens 49152 --max-cny 45 --out <runs>/locomo
node --env-file=.env --experimental-transform-types scripts/bench/judge.ts <runs>/locomo --concurrency 24
node --experimental-transform-types scripts/bench/summarize.ts <runs>/locomo
node --experimental-transform-types scripts/bench/plot-doc.ts <runs>/locomo <runs>/lme docs/pr-assets/doc-memory-20261014
```

`--max-cny` 是该运行目录的累计上限（包含此前在同一目录里的花费）。

代码改动：
- `scripts/bench/doc.ts`（新增）：原文组与 `doc:<KiB>` 组，作答记录与 run.ts 同格式。
- `scripts/bench/judge.ts`：OpenAI 辅助模块改为只在指定 OpenAI 评分模型时加载，未安装依赖时默认的 DeepSeek 评分也能运行。
- `scripts/bench/plot-doc.ts`（新增）：生成本报告的 `data.json` 与两张图。
