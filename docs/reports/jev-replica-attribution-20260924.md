# 外挂 DSH 副实例是不是带来提升的关键设计

日期：2026-09-24 · 分支：`codex/jev-replica-practice`（本地提交，不发布、不推送）· 数据：[第二轮报告](jev-v4-20260923.md)的已有运行，本次只做离线分析，没有新的模型调用

## 结论

1. **是关键设计之一，但起作用的是副实例承担的职能**：主模型回答之前，副实例在主模型的上下文之外把这一轮需要的记忆找出来，组成一份小 View，事实变了就把旧的撤掉。只换架构、副实例不用 JEV 只用 BM25，一周连续对话里“回答用到必要事实”就从 76% 升到 85%（3600 条记忆时 42% → 79%），过时回答 7 → 3，主模型 token −88%，费用 −71%。
2. **收益不来自“另起一个进程”本身**：
   - 按同样大小的 View 算，在主进程里直接对全部记录做一次 BM25，覆盖的必要证据和 BM25 副实例相当（66% vs 68%）。
   - 同一套 JEV 策略在哪个进程里跑，都会产出同一份 View。
   - 两个进程之间的桥，每轮只多约 0.11 秒。
3. **独立实例这种形态的价值在工程上**：
   - 在现在的实现里，副实例是不改动主 Agent 就能让 JEV 组 View 的方式。
   - 另外还有故障隔离、凭据分离、可以用更便宜的模型、预读在主模型之外进行。
   - 可以异步准备 View，但还没用上：现在主模型每轮都等 View，副实例任务的 2 秒在关键路径上。
4. **质量的大头来自副实例里的判断（JEV）**：同样两三条的 View，JEV 覆盖 90% 的必要证据，BM25 取前 2–3 条只有 52–64%。隐式指代 65% → 100%，过时回答 3 → 0。
5. **一次性问答里，副实例单独用不比主模型自己查好**：LoCoMo 87.0% vs 86.5%，LongMemEval 75.0% vs 75.0%；只用 BM25 的副实例更差。但两者错在不同的题上，合用（v4t）是最好的记忆方案（90.9% / 88.9%）。
6. **适用范围**：连续对话、事实会变、记忆越积越多时，副实例是正向且关键的；问答场景要和主模型自查搭配；历史短到能整段放进上下文时，整段放入更好（LoCoMo 95.1%）。

## 1. 怎么拆

- **逐步替换**，每一步只换一样：
  1. 仅主 DSH：主 DSH 自己挂 Source，看 Host 自带的 View，用工具自己查。
  2. 副实例 · BM25：只换架构。每轮由副实例组 View，判断只用 BM25，不调 JEV。
  3. 副实例 · JEV（v4）：换判断。
  4. v4 + 主模型自查（v4t，只在问答里）。
  5. 参考：整段放入上下文。
- **机制**：对每条必要事实，检查三件事：
  - 它在不在主模型收到的 View 里（仅主 DSH 看 Host 自带的 View）；
  - 主模型这一轮有没有自己查（一轮里多于一次模型请求，即调用了记忆工具）；
  - 回答有没有用到（沿用第二轮的 DeepSeek 评审结果）。
- **进程边界**：
  - 离线复算：用插件同一个 BM25（`LexicalIndex`，查询同样取最近三句用户消息，按 1 / 0.5 / 0.25 加权），在主进程里对全部记录检索，按 View 的条数取前 k 条。
  - 延迟拆成三段：主模型、副实例任务、其余（桥 + Host）。

## 3. 为什么副实例在对话里有效：主模型自己找记忆的缺口

| 一周场景（900 条 / 3600 条） | 仅主 DSH | 副实例 · BM25 | 副实例 · JEV（v4） |
|---|---:|---:|---:|
| 必要事实就在主模型收到的 View 里 | 18% / 18% | 68% / 62% | 90% / 58% |
| 需要记忆的轮次里，主模型自己查了 | 52% / 46% | 不需要查 | 不需要查 |
| 不在 View、主模型查了，回答用到 | 71% / 29% | — | — |
| 在 View 里，回答用到 | 100% / 100% | 96% / 96% | 100% / 100% |
| 过时回答（其中旧记录就在当前 View 里） | 7（0） / 6（0） | 3（3） / 4（4） | 0 / 0 |
| 每轮主模型输入 token | 11.0 万 / 9.4 万 | 1.3 万 / 1.4 万 | 1.3 万 / 1.2 万 |

- **Host 自带的 View 放的是各 Source 最新的记录，不是这一轮要用的**：必要事实只有 18% 在里面，其余要主模型自己去找。多会话闲聊里也是 17%。
- **主模型只在约一半需要记忆的轮次里去查**（52%，3600 条时 46%）；其余时候凭上下文里已有的内容作答。多会话闲聊里每段对话都短、上下文里没有积累，它 90% 的轮次都去查，但查到并用上的只有 55%。
- **记忆一多，自己查就不灵了**：不在 View、主模型查了的事实，900 条时回答用到 71%，3600 条时只有 29%。
- **过时回答全部来自主模型自己查到或上下文里残留的旧内容**（之前的工具结果、之前的回答），7 次里没有一次是旧记录就在当前 View 里。上下文里新旧两份都在，没有东西告诉模型哪一份作废了。
  - 副实例每轮重组 View：JEV 把被取代的记录标为“已不再成立”并撤下，过时回答为 0；
  - BM25 判断不了取代关系，旧记录在它的 View 里出现了 57/82 次，其中 3 次被当成了当前。
- **在 View 里的事实，主模型几乎都会用上**（96–100%），所以关键在于每轮 View 里有没有。副实例把“要不要去查、查什么”从主模型手里拿走，每轮在回答之前一定先检索一次，这正对着上面三个缺口。

## 4. 是“另起一个实例”，还是“每轮替主模型组 View”

### 4.1 不用副实例、在主进程里直接检索（离线复算）

同样的 70 轮，同一个 BM25，在主进程里对全部记录（含对话中途新增和改写的）检索，取前 k 条（900 条 / 3600 条）：

| 前 k 条 | 2 | 3 | 5 | 8 |
|---|---:|---:|---:|---:|
| 必要事实在前 k 条里 | 52% / 52% | 64% / 64% | 66% / 66% | 71% / 74% |
| 旧记录出现在前 k 条里（共 41 次机会） | 14 / 14 | 20 / 20 | 27 / 26 | 33 / 30 |

对照副实例实际交付的 View：

| | 平均条数 | 必要事实在 View 里（900 条 / 3600 条） |
|---|---:|---:|
| 副实例 · BM25 | 4.5 | 68% / 62% |
| 副实例 · JEV（v4） | 2.4 / 1.8 | 90% / 58% |
| 副实例 · JEV 全量扫描 | 2.2 / 1.7 | 93% / 74% |

- **同是 BM25，主进程直接检索与副实例不相上下**（前 5 条 66% vs 副实例 68%）。所以 BM25 副实例相对仅主 DSH 的提升，来自“每轮先检索、只给主模型一份小 View”，不来自独立实例：台账、滞回、按词检索这些副实例内部机制，在 BM25 下没有多带来覆盖。
- **同样两三条，JEV 90%，BM25 52–64%**：小 View 能不能准，取决于判断。
- **3600 条时，副实例的覆盖受读取预算限制**：记录型 Source 一次列举不完，v4 的 View 只有 58%，低于主进程直接检索前 3 条的 64%。离线复算假设主进程能对全部记录建索引，是上限；真实部署要通过 Route 读取，同样受预算限制。这是副实例“读得到多少”的问题，不是进程边界的问题。

### 4.2 进程边界的时间开销（低负载复测，中位数）

| | 总计 | 主模型 | 副实例任务 | 其余（桥 + Host） |
|---|---:|---:|---:|---:|
| 仅主 DSH | 1.55 秒 | 1.50 秒 | — | 0.05 秒 |
| v4 | 2.98 秒 | 0.93 秒 | 2.03 秒 | 0.16 秒 |

- 两个进程之间的桥（按文件轮询，间隔 50 毫秒）每轮多约 0.11 秒。
- 主模型反而更快（0.93 秒 vs 1.50 秒）：上下文小，也不用一轮轮调工具。
- 副实例任务的 2 秒在关键路径上：召回约 1.1 秒，JEV 判断约 0.4 秒（均值）。它是选择本身的开销，换到主进程里也一样；主模型要等本轮消息对应的 View（`maxRevisionLag` 为 0）。

### 4.3 独立实例在质量和费用之外提供了什么

- **接入 JEV**：
  - 副实例由 JEV 驱动的 agent loop（`JevAgentLoop`）运行，自然策略就注册在它上面；主实例跑的是普通的 `AgentLoop`。
  - 副实例的选择以一个 `replica` 类型的 Source 进入主实例的 Host View，主 Agent 不用改，也不需要记忆工具。
  - 要把同一套策略搬进主进程，得把它改写成 Host 的 View 策略，不是改一个配置。
- **故障隔离**：3600 条的运行里，各组有 1–4 次副实例任务失败（服务端 520、JEV 超时），主模型沿用上一份 View 照常回答。
- **凭据与模型分离**：测试框架里主进程拿不到 JEV 的 key；召回用的是副实例自己的 LLM（可以换更便宜的模型），它的提示前缀稳定，缓存命中 95–96%，与主模型的缓存互不干扰。
- **在主模型之外预读**：对话开始前的预热巡检和日期回填都在副实例里进行。
- **还没用上的异步**：Bridge 支持 `maxRevisionLag`，允许主模型先用上一轮的 View 作答、副实例在后台准备下一份。这里的全部测量都等本轮的 View。这是独立实例唯一可能在延迟上带来额外收益的地方，还没有测。

## 5. 问答基准：副实例的 View 和主模型自查是互补的

| | LoCoMo（385 题） | LongMemEval_S（36 题） |
|---|---:|---:|
| 副实例 v4 单独 | 87.0% | 75.0% |
| 仅主 DSH（主模型每题都自己查） | 86.5% | 75.0% |
| 只有 v4 答对 | 24 题 | 4 题 |
| 只有仅主 DSH 答对 | 22 题 | 4 题 |
| 两者都错 | 28 题 | 5 题 |
| 任一答对（理论并集） | 92.7% | 86.1% |
| 合用（v4t） | **90.9%** | **88.9%** |
| v4t 中主模型又自己查的比例 | 29% | 53% |
| v4t 准确率：没查 / 查了 | 96.7% / 76.4% | 94.1% / 84.2% |

- 问答题明确、自成一句，主模型拿着问题去查很有效（它每题都查）；副实例按对话挑证据。两者错在不同的题上。
- 合用时，LoCoMo 71% 的题、LongMemEval 47% 的题副实例的 View 已经够用，主模型直接回答，正确率 96.7% / 94.1%；其余的题主模型再自己查。
- LongMemEval 上合用（88.9%）高于两者各自答对的并集（86.1%），追平整段放入上下文。

## 6. 回答

- **副实例承担的职能是关键设计**：
  - 每轮在主模型回答之前、在它的上下文之外，先把记忆找好、组成一份小 View，并撤掉过时的；
  - 它补上的是主模型自己找记忆的三个缺口：不去查、查不准、分不清新旧；
  - 带来的是主模型上下文 −88%、记忆越多优势越大（3600 条时 42% → 79–82%）、过时回答归零（配 JEV）。
- **独立实例这种形态本身不产生这些收益**：同样的选择放在主进程里，View 相同；进程开销约 0.1 秒/轮。它是现在接入 JEV、又不改动主 Agent 的方式，并带来隔离、凭据分离、换模型、后台预读等工程上的好处。
- **副实例里的判断决定收益大小**：没有 JEV，副实例在问答里比主模型自查还差；有了 JEV，小 View 足够准。
- **最佳用法**：连续对话用 v4；问答用 v4t（副实例 View + 主模型可自查）；历史短、同一段历史反复被问时，整段放入上下文。

值得补的实验（需要重新提供 API key）：

1. **异步副实例**：`maxRevisionLag` 设为 1，看能否把 2 秒的选择移出关键路径、质量掉多少。这是独立实例可能额外带来收益的唯一一处。
2. **主进程版本**：把自然策略写成 Host 的 View 策略、在主进程里调用 JEV，直接验证“同一 View、同一结果”。
3. **大记忆下的读取**：给副实例一个可检索的 Source 索引，代替受预算限制的逐页列举（3600 条时 v4 的 View 覆盖 58%，低于主进程直接检索前 3 条的 64%）。

## 局限

- 一周场景每组 1–2 次运行，3600 条只有 1 次；问答基准只取代表性子集（LoCoMo 3/10 段，LongMemEval 36/500 题），判分模型是 DeepSeek。
- “主模型自己查了”按一轮里的模型请求数近似；主模型通过工具读到的内容不计入“在 View 里”。
- 离线复算是主进程检索的上限（假设能对全部记录建索引），且只覆盖 BM25；“JEV 策略放在哪个进程都一样”是按构造推断，没有直接运行。
- 多会话闲聊没有 BM25 副实例这一组，架构这一步只在一周场景和问答基准上拆了。
