# JEV 记忆第二轮：复杂场景、缓存监控、方案选择与公开基准

日期：2026-09-23 · 分支：`codex/jev-replica-practice`（本地提交，不发布、不推送）

## 结论

1. **推荐方案 v4**：JEV 缓存方案召回（副本 LLM 一次列出候选并给检索词）+ JEV 两问判断 + 门控 0.3 + Host delta 投递 + 只向能调用的模型展示记忆路由 + 大型 Source 按日期翻页；底层记忆用带日期的会话笔记。问答为主的场景再让主模型保留记忆工具（§9.4）。
2. **复杂场景（一周连续对话，70 轮、10 处事实中途变更）**，相对仅主 DSH：回答用到必要事实 96% vs 76%，把过时信息当作当前 0/82 vs 7/82，主模型 token −88%，主 + 副 token −59%，费用 +11%。多会话闲聊里 v4 费用 −38%、p95 −39%，事实使用 96% vs 61%。
3. **缓存监控**：replace 投递的缓存损失几乎全部来自“快照被替换”造成的改写（命中 78%）；delta 回到 97%，长工具任务里每轮首个请求的未命中从 2.3 万 token 降到 2.8k。批量退役不可能减少未命中总量，已删除。副本召回清单的缓存命中 95–96%。
4. **规模（4 倍语料 + 干扰）**：基线事实使用从 76% 跌到 42%；v4 保持 82–86%。关键是召回调用给检索词（比 JEV 选词高 17 个百分点），全量扫描质量相近但费用是基线的 8 倍。
5. **公开基准**（DeepSeek 判分，代表性子集）：LongMemEval_S 上“v4 + 主模型可查工具”88.9%，与长上下文全量持平、费用 60%；纯 v4 75%（加日期翻页前 55.6%）。LoCoMo 每段只有约 2 万 token，整段放进上下文最好（95%，每题 $0.00034）；v4 87%，与仅主 DSH 相当、费用约 1/4.6。LoCoMo 上“v4 + 主模型可查工具”90.9%，是最好的记忆方案。
6. **两处更正**：测试框架每轮“恢复”会话，让基线每轮重复注入同一份 View，上一轮高估了基线费用（已修正，本报告全部基于修正后数据）；View 的路由说明误导没有工具的主模型把工具调用写成回答，最多占三分之一的回答（已在 Host 修正）。

## 2. 先更正：上一轮的基线被测试框架高估了

测试框架原来每轮都“恢复”一次会话。Host 在会话开始时会清空“上一次注入的 View”，于是每轮都重新注入一份内容完全相同的 View：32 轮长对话里，仅主 DSH 的上下文里有 32 份相同的 3.2 万字 View（31 份与上一份逐字相同）。真实使用时会话在轮次之间一直活着，不会这样。修正后（会话内保持同一个 Agent）重跑基线：

| 64 次多会话闲聊，开启思考 | 修正前 | 修正后 | 变化 |
|---|---:|---:|---:|
| 每次输入费用 | $0.00278 | $0.00151 | −46% |
| 主模型未命中 / 命中 token | 12.1k / 106k | 6.4k / 30.7k | −47% / −71% |
| 延迟 p95 | 15.0 秒 | 11.4 秒 | −24% |
| 必要证据出现在请求里 | 53% | 50% | 基本不变 |

上一轮“JEV 缓存方案费用 −57%”主要来自这个假象。本报告所有基线都是修正后的；方案组也全部用修正后的框架重跑。

## 3. 缓存监控

### 3.1 怎么测

- **实际命中率**：DeepSeek 返回的缓存读取 token ÷ 全部输入 token（按 token 加权）。
- **理论上限**：把请求拆成 tools、system 和每条消息，逐段算摘要；与同一会话里任一更早请求的最长相同前缀（按字符）÷ 请求总字符。这是提示布局决定的上限，和服务端缓存状态无关。
- **未命中原因**：最长相同前缀之后第一个不同的部分。只是在末尾多了新内容记为“只多了新的尾部”；前面某条记忆快照被替换记为“快照被替换（改写）”。
- **副本召回调用**：每次记录清单字符数和与上一次清单相同的前缀字符数。

### 3.2 投递方式：replace 的缓存损失几乎全部来自改写

同一个“一周”场景（70 轮 × 2 次重复），同一个选择器，只换 Host 的投递方式：

| 选择器 | 投递 | 主模型命中率 / 理论上限 | 每轮未命中 token | 每轮输入 token |
|---|---|---:|---:|---:|
| BM25 | replace | 79% / 90% | 1.0k | 4.5k |
| BM25 | append | 97% / 97% | 0.8k | 25.4k |
| BM25 | **delta** | **97% / 97%** | **0.4k** | 12.8k |
| JEV 缓存方案 | replace（v3） | 78% / 90% | 0.9k | 4.2k |
| JEV 缓存方案 | append | 97% / 97% | 0.8k | 24.2k |
| JEV 缓存方案 | **delta** | **97% / 97%** | **0.5k** | 13.8k |
| （基线）仅主 DSH | 追加 | 99% / 98% | 1.6k | 109.8k |

![命中率随轮次](../pr-assets/jev-v4-20260923/week-cache-hit-by-turn.svg)

![每轮上下文](../pr-assets/jev-v4-20260923/week-cache-input-by-turn.svg)

![未命中原因](../pr-assets/jev-v4-20260923/week-cache-miss-by-cause.svg)

- replace 组 120 个请求的首个改写都是“快照被替换”：替换旧快照会让它之后的全部内容重新计算。
- append 从不改写，但每次变化都追加一整份快照，上下文涨到 replace 的 5–6 倍。
- delta 只追加变化的块：命中率和 append 一样，未命中量最少，上下文只有 append 的一半。
- **批量退役（上一轮的 `snapshotRetention`）不可能减少未命中总量**：退役一批快照时，要从最早那份快照往后全部重算，N 轮攒下的改写在同一次全部付掉。只要最终退役，每段轨迹都要重算一次；只有从不改写（append / delta）才省。所以这一轮删掉了它。

### 3.3 长工具任务：改写的代价最大

真实工具长任务（活动筹备、网页项目、技术调研，各 32 次输入；主模型不开思考，与上一轮设定一致）。每次输入平均 4–5 个主模型请求，上一轮的工具轨迹可达数万 token：

| 模式 | 每次输入费用 | 主模型命中率 / 理论上限 | 每次输入首个请求的未命中 | 其中“快照被替换” | 外部验收通过 |
|---|---:|---:|---:|---:|---:|
| 仅主 DSH（基线） | $0.00947 | 98% / 97% | 0.4k | 0 | 62/83（75%） |
| v3（replace） | $0.01190 | 94% / 92% | 23.1k | 21.6k | 80/83（96%） |
| **缓存方案 · delta** | **$0.01055** | **98% / 97%** | **2.8k** | **0** | **81/83（98%）** |
| v4 | $0.01142 | 98% / 97% | 2.9k | 0 | 80/83（96%） |

- replace 每次输入的第一个请求要重算约 2.2 万 token：退掉上一份快照，就把上一轮整段工具轨迹一起作废了。delta 把它降到 1/8，费用比 v3 低 11%。
- 长任务的费用主要是主模型输出（每次输入约 7–9k token）；v4 在这组任务里主模型多执行了一些请求（每次输入 5.3 次对 4.9 次），所以总费用反而略高于 delta。长任务噪声大，这是一次运行。
- 外部验收：记忆方案 96–98%，基线 75%。

### 3.4 副本召回调用的缓存

JEV 缓存方案的召回调用把整个台账（约 560 条，按首次出现排序）放在提示最前面。一周场景里每次约 2.5 万 token，实际命中 95–96%，理论上限 97–98%。台账条目内容变了（例如展开卡片正文、文件被改写）时会在中间改写清单，这是剩下的几个百分点。

- 主模型 token 降 88–96%：副本只交付选中的证据，而基线每轮要读整份 View 和工具结果（每轮输入 11 万 token，几乎全靠缓存才便宜）。

- 全量扫描质量与缓存方案相当（97%），费用是 v4 的 4 倍，不适合做默认。
- “delta + 门控”和“全量扫描”各有 4 次把过时信息当作当前，全部出在改签后的两轮（`train-3`、`leave-home-3`，同一次重复）。逐轮核对副本轨迹：这两轮**没有**被门控跳过，走的是完整流程，是 JEV 判断没有把旧车票撤回，新旧车次同时留在 View 里。门控本身在记录有变化时从不生效，这次没有造成过时回答；这类“判断偶发漏撤”在 v3、delta、v4 的两次重复里没有出现，样本量小，应视为判断的随机误差而不是方案差异。

## 6. 发散方案逐个看

### 6.1 门控：先问 JEV 一句“当前 View 够不够”

- **离线校准**（`scripts/natural/gate-study.ts`）：用已有运行的 144 个“上一轮 View + 当前问题”配对，其中 106 个确实需要补充记忆。JEV 对这 106 个给出的“还需要更多”最低为 0.43。阈值 0.3：零漏判，跳过 38 个已覆盖轮次中的 19 个；0.5 开始漏判。每次门控约 920 JEV token。
- **规则**：只有当本轮观察没有发现任何记录新增、修改或删除，且 JEV 的“还需要更多”低于 0.3 时，才原样重发当前 View。
- **实测**（一周场景，两组共 280 轮）：跳过 43 轮（14–16%），被跳过轮次涉及 8 组必要证据，只漏 1 组（第二次重复的 `cane-2` 问手杖口令，上一轮 View 里没有）。门控省下的是整条召回与判断链路，View 不变也保住了主模型缓存。

### 6.2 召回调用顺带给检索词（v4 的主要省钱点）

v3 每轮 JEV 输入的拆分：选检索词 6.1k token（39%），判断 9.5k（61%）。选词请求本身是“从不超过 40 个候选词里挑词”，大头是同一段判据重复了 40 遍。v4 让已经在跑的召回调用在同一次回答里给出至多 4 个检索词（`SEARCH:` 一行），去掉这次 JEV 调用：JEV 每轮 16.6k → 10.6k token，费用 −29%，质量不降（§4）。召回调用可以提出对话里没出现过的词（问“几点出门”时想到“打车”），这是 JEV 在代码生成的候选里挑词做不到的。

### 6.3 JEV 缓存方案 vs JEV 全量扫描方案

两者质量相当（一周场景 96% vs 97%，闲聊 96% vs 96%）；全量扫描每轮要对台账里约 560 条各问一次，JEV 输入约 8.4 万 token，费用是 v4 的 4 倍。台账越大差距越大（§7）。默认用缓存方案。

### 6.4 只用 BM25 的副本（无 JEV）

最便宜（一周场景 −71%），但判断不了“已不再成立”，也接不住隐式指代：用到必要事实 85%，隐式指代只有 65%，过时回答 3/82。它适合作为 JEV 不可用时的降级模式，不适合做默认。这一轮 JEV 额度中途用完过一次，这个降级路径正好派上了用场。

## 7. 规模：4 倍语料 + 同实体干扰

### 7.1 副本能看到多少（离线，`scripts/natural/coverage.ts`，不调模型）

| 语料 | 行数 | 预热 9 次后台巡检后的台账 | 其中含关键证据 |
|---|---:|---:|---:|
| 1 倍（每个 Source 100 行） | 900 | 562 条，5 个记录型 Source 全部列举完 | 44 / 66 |
| 4 倍（每个 Source 400 行） | 3600 | 704 条，5 个记录型 Source 均为 partial | 21 / 66 |

平台的每个 View 对每条 Route 有调用预算（记录型 Source 8 次 × 每页约 16 条），读游标又绑定在 View 上，所以一个大 Source 无法跨任务续扫。这一轮改为：一次列举不完的 Source 标记为 partial，以后只读最新条目并按词检索，不再每轮重读同样的前几页（之前前台每轮要在这上面花掉约 40 次读取，总预算 64）。一开始我尝试过跨任务续扫，离线覆盖率检查发现游标在下一个 View 里会被拒绝，就撤回了。

### 7.2 一周场景放到 4 倍语料（1 次运行）

语料 3600 行（25% 同实体干扰），其余与 §4 相同，各 1 次运行：

| 相对仅主 DSH（基线） | 缓存方案 · delta | v4 | 全量扫描 · delta | BM25 · delta |
|---|---:|---:|---:|---:|
| 费用 | +113% | +97% | +738% | −64% |
| 主 + 副 token 合计 | −22% | −26% | +52% | −85% |
| 主模型缓存命中率（基线 98%） | 97% | 97% | 97% | 97% |
| 命中：必要证据进入上下文（基线 40%） | 55% | 58% | 74% | 62% |
| 命中：回答用到必要事实（基线 42%） | 65% | 82% | 84% | 79% |
| 过时信息被当作当前（基线 6/41） | 0/41 | 0/41 | 4/41 | 4/41 |

| 每次输入的绝对费用 | 1 倍语料 | 4 倍语料 |
|---|---:|---:|
| 仅主 DSH | $0.00081 | $0.00069 |
| v4 | $0.00090 | $0.00135 |
| 全量扫描 · delta | $0.00372 | $0.00576 |

- 语料放大 4 倍，基线“用到必要事实”从 76% 掉到 42%：它的 View 只能露出最新的一部分记录，工具检索又常常找不准。
- v4 从 96% 降到 82%（修正路由说明后单独补跑一次：86%，证据进入上下文 73%；那次机器负载低、没有出现服务端 520 和超时，差别主要来自这两点和运行间波动，不应归功于路由修正）。
- v4 和“缓存方案 · delta”的唯一区别是检索词来源。账本装不下全部证据时，召回调用提出的检索词让事实使用率高出 17 个百分点（82% vs 65%），这是 v4 在规模上的关键。
- 全量扫描质量最高（84%），但要对台账逐条问 JEV，每轮 13.2 万 JEV token，费用是基线的 8 倍多。v4 的召回提示长到约 5 万 token，但 96% 命中缓存，费用只涨 50%。
- 本次运行中各方案各有 1–4 次副本任务失败（服务端 520、JEV 20 秒超时），对应轮次沿用了旧 View。

## 8. 一个隐藏的失败：模型把工具调用写成了回答

逐条检查答错的题时发现，一部分“回答”其实是 DeepSeek 的原始工具调用标记（`<｜｜DSML｜｜ invoke name="mnemon_view_route">…`）。原因是 Host 在 View 末尾附带了路由说明（`MNEMON VIEW ROUTES … use mnemon_view_route`），而副本方案里的主模型根本没有这些工具；View 里找不到答案时，开启思考的模型就把调用当成正文输出了。

| 运行 | 受影响的回答 |
|---|---|
| 一周场景（各副本方案） | 0–9 / 140 |
| 多会话闲聊 | 0–1 / 64 |
| 4 倍语料 · v4 | 4 / 70 |
| LoCoMo · v4 笔记 / 全量扫描混合 / BM25 原文 | 16 / 385 · 70 / 385 · 126 / 385 |

修正（Host，`src/core/turns.ts`、`src/host/lifecycle.ts`）：生成 View 文本时由 Host 告诉核心层当前 Agent 能调用哪些工具；`mnemon_view_route` / `mnemon_view_action` 都不可用时不附带路由说明，具名工具也只列可调用的。主模型能用工具时（仅主 DSH）不受影响。修正后的补跑见 §7.2 与 §9。

## 9. 公开基准：LoCoMo 与 LongMemEval（代表性子集）

### 9.1 怎么接进这套架构

- **一份记忆 = 一个工作区**：LoCoMo 每段对话一个工作区，其全部问题在同一记忆上各开一个新会话提问；LongMemEval 每道题有自己的历史，一题一个工作区。
- **底层记忆模式**（`scripts/bench/seed.ts`）：
  - 原文：每条消息作为导入的会话历史写入 sessions Source，消息正文前带“#会话号 · 日期”；
  - 笔记：写入时由模型把每个会话整理成带日期、自成一句的事实（`scripts/bench/notes.ts`，按会话缓存），按不超过约 600 字切块写入 journal，块头为“Conversation #n on 日期”；
  - 混合：两者都写。
- **对照**：长上下文全量（整段历史直接放进提示，DeepSeek 上下文 1M）；仅主 DSH（主 DSH 挂 Source，自己用 Host 工具查）；副本方案 v4 / 全量扫描 / BM25。主模型都开启思考，提示词相同。
- **判分**：LoCoMo 用 Mem0 等工作采用的宽松 CORRECT/WRONG 判定，另算词级 F1；LongMemEval 用它 `evaluate_qa.py` 的分题型是/否判定。**判分模型是 DeepSeek**（论文用 GPT-4o / 4o-mini），绝对值不宜与论文数字直接比较。
- **选组**：LoCoMo 取短、中、长三段（conv-30 / conv-26 / conv-41，共 385 道非对抗题）；LongMemEval_S（清洗版）每种题型按 id 哈希取 6 道，共 36 道。

### 9.2 LoCoMo（每段对话约 2 万 token）

![LoCoMo](../pr-assets/jev-v4-20260923/locomo-accuracy.svg)

| 组 | 准确率 | F1 | 证据进入上下文 | 每题费用 | p50 / p95 |
|---|---:|---:|---:|---:|---:|
| 长上下文全量 | **95.1%** | 49.0% | 100% | **$0.00034** | 1.4 / 5.6 秒 |
| v4 + 主模型可查工具（§9.4） | 90.9% | 28.2% | 89% | $0.00217 | 4.0 / 11.0 秒 |
| 仅主 DSH · 笔记 | 86.5% | 17.9% | 84% | $0.00355 | 9.2 / 30.0 秒 |
| **v4 · 笔记（路由说明修正后）** | **87.0%** | 41.5% | 88% | $0.00077 | 3.2 / 7.0 秒 |
| v4 · 笔记 | 86.5% | 34.1% | 88% | $0.00079 | 3.0 / 5.5 秒 |
| v4 · 混合 | 84.4% | 34.1% | 86% | $0.00095 | 3.2 / 5.2 秒 |
| 全量扫描 · 笔记 | 86.5% | 33.5% | 89% | $0.00147 | 2.9 / 5.4 秒 |
| v4 · 原文 | 33.2% | 14.7% | 17% | $0.00079 | 3.4 / 10.8 秒 |
| BM25 · 笔记 | 79.7% | 27.8% | 86% | $0.00038 | 2.2 / 8.8 秒 |
| BM25 · 原文 | 22.3% | 9.1% | 36% | $0.00057 | 4.4 / 16.0 秒 |

- **记忆模式**：笔记明显好于原文（v4 87% vs 33%，BM25 80% vs 22%）。一条消息太碎，单独拿出来既难召回、也难读懂；会话笔记把事实和日期放在一起。混合不比笔记好。
- **在这个规模上，最好的“记忆模式”是整段放进上下文**：同一段对话的全部问题共享同一个很长的前缀，几乎全靠缓存命中，每题只要 $0.00034，准确率 95%。记忆系统在这里赢不了。
- v4 与仅主 DSH 准确率相当，费用约 1/4.6，p95 约 1/4。
- 全量扫描一开始只有 68%：它的 JEV 扫描把每条记忆截成 120 字，对 600 字的笔记块太短。改为与召回清单相同的摘录长度（`listing`）后为 86.5%，与 v4 相同，但费用约为 v4 的 2 倍。
- v4 的错题：日期换算错误（笔记把“5 月 25 日前的那个周日”记成了 20 日）、证据未被召回，各占约一半。

### 9.3 LongMemEval_S（每题一份约 12 万 token 的历史）

每道题约 48 个会话、约 49 万字符；笔记模式下每题约 270–350 条笔记块。

![LongMemEval](../pr-assets/jev-v4-20260923/longmemeval-accuracy.svg)

| 组 | 准确率 | 证据进入上下文 | 每题费用 | p50 / p95 | 知识更新 | 跨会话 | 时间推理 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 长上下文全量 | **88.9%** | 100% | $0.01355 | 3.1 / 10.2 秒 | 67% | 83% | 100% |
| **v4 + 主模型可查工具** | **88.9%** | 76% | $0.00813 | 7.0 / 15.6 秒 | 83% | 83% | 100% |
| 仅主 DSH · 笔记 | 75.0% | 89% | $0.00306 | 6.2 / 15.4 秒 | 83% | 50% | 83% |
| v4 · 笔记 | 75.0% | 79% | $0.00622 | 4.9 / 8.1 秒 | 33% | 50% | 83% |
| v4 · 混合 | 75.0% | 76% | $0.00631 | 4.2 / 6.5 秒 | 50% | 50% | 83% |
| 全量扫描 · 笔记 | 72.2% | 76% | $0.00327 | 3.8 / 7.1 秒 | 50% | 50% | 67% |
| BM25 · 笔记 | 63.9% | 74% | $0.00038 | 2.1 / 4.4 秒 | 83% | 50% | 33% |
| v4 · 笔记（无日期翻页） | 55.6% | 63% | $0.00348 | 4.5 / 9.5 秒 | 17% | 33% | 67% |

（每种题型 6 题；单会话用户 / 助手 / 偏好三类见图。）

- **一开始 v4 只有 55.6%**：每题 270–350 条笔记超过了一个 View 能列举的约 128 条，journal 被标为 partial，副本只看得到最新的一段。加上按日期向前翻（`until`）后，预热巡检就能把全部笔记读进台账：**55.6% → 75.0%**，证据进入 View 62.5% → 79.2%。中途还发现记录型 Source 只有 `daily` 作用域才保存日期，笔记改为按天写入后日期翻页才生效。
- **长上下文全量最好（88.9%）**：DeepSeek 在 12 万 token 的完整历史上表现很好，代价是每题 $0.0136。
- **v4、混合、仅主 DSH 都在 75% 左右**，各有强弱：仅主 DSH 的 Host View 天然展示最新记录，知识更新题 83%；v4 在这类题只有 33%，错题里 View 往往拿到了旧值却没拿到新值（有一题 JEV 正确地把旧记录标成“已不再成立”，但替代它的新记录没被召回）。
- **成本倒挂**：这里每道题都是一份全新的记忆，v4 的召回清单（约 300 条 × 600 字）没有任何缓存可用，按未命中价计费，每题 $0.0062，反而比 JEV 全量扫描（$0.0033，JEV 单价低）和仅主 DSH（$0.0031）贵。持续对话里同一份台账每轮复用、命中 95% 以上（§3.4），结论相反。**一次性问答选全量扫描，持续对话选缓存方案**。
- v4 的错题主要是：召回漏掉证据（跨会话计数、知识更新里的新值）、笔记丢了细节（记下“用了 5 美元优惠券”，没记在哪家店）、回答过于保守（有旧值和“快到 1300”却答“没有当前数据”）。

### 9.4 最好的组合：副本交付 View，主模型仍可自己查

v4 的短板（知识更新拿到旧值、跨会话计数不全）恰好是仅主 DSH 的长处：Host 自己的 View 露出最新记录，主模型还能按需用工具检索。把两者合起来（`replica-v4t`）：副本照常交付 JEV 挑好的笔记，主 DSH 同时挂着 Source、能调用 `mnemon_view_route`（路由说明修正后，只有这时才会展示路由）。

在 LongMemEval 上它是唯一追平长上下文全量的记忆方案：**88.9%**，每题 $0.0081（全量的 60%）。多数题 View 已经够用、主模型一次回答；缺东西时自己查一两次。代价是 p95 15.6 秒（多了工具往返）和比 v4 高约 30% 的费用。

LoCoMo 上同样是最好的记忆方案：**90.9%**（v4 87.0%，仅主 DSH 86.5%），每题 $0.00217；但这一规模下仍不及整段放进上下文（95.1%，$0.00034）。

## 10. 延迟（低负载复测）

主实验大多是十几组并行、机器交换区接近用满时测的，延迟被放大。单独用低负载复测一次：一周场景前 24 轮，只跑三组，开启思考。

| 组 | 平均 | p50 | p95 | 副本任务（平均 / p95） |
|---|---:|---:|---:|---:|
| 仅主 DSH（基线） | 2.3 秒 | 1.6 秒 | 4.7 秒 | — |
| v3（此次带门控 *） | 3.5 秒 | 3.7 秒 | 4.8 秒 | 1.9 / 2.5 秒 |
| **v4** | **3.1 秒** | **3.0 秒** | **4.3 秒** | 1.8 / 2.3 秒 |

- v4 的副本任务平均 1.8 秒：召回 1.3 秒、按词检索 0.13 秒、JEV 判断 0.5 秒；v3 的检索阶段要多一次 JEV 选词（0.49 秒）。
- 中位延迟比基线多约 1.4 秒（副本在关键路径上），p95 反而低 9%：基线偶尔要连续调用几次工具。

\* 门控默认值改为 0.3 后，这次复测的 v3 组也被门控（24 轮中 4 轮）。之后脚本里 v3 系列的组都显式写了 `gate: 0`，与主实验一致。

## 11. 最佳方案与默认值

**推荐：v4**，即

| 层 | 选择 | 依据 |
|---|---|---|
| 召回 | JEV 缓存方案：整个台账作为稳定前缀，一次副本 LLM 调用列出候选并给出检索词（`recall: 'llm'`，`termsFrom: 'recall'`） | 与全量扫描质量相当，费用约 1/4；规模变大时检索词让事实使用率高出 17 个百分点 |
| 判断 | JEV 两问（需要吗 / 已不再成立吗），同批可见，滞回进出 | 一周场景过时回答 0/82，基线 7/82 |
| 门控 | `gate: 0.3`，且只在没有任何记录新增、修改或删除时生效 | 离线 106 个“需要更多”零漏判；实测跳过 14–16% 的轮次，漏 1 组证据 |
| 投递 | Host `snapshotDelivery: 'delta'` | 主模型缓存命中 97%（replace 78%），长任务每轮首请求未命中降到 1/8 |
| View 文本 | 只向能调用的 Agent 展示记忆路由 | 消除“把工具调用写成回答”（最多占回答的三分之一） |
| 大型 Source | 一次列举不完标为 partial；有日期的按日期向前翻（`until`） | 前台不再白白重读；LongMemEval 的账本从 128 条补全到约 300 条，准确率 55.6% → 75.0% |
| 底层记忆 | 长历史用带日期的会话笔记；原文只适合检索细节 | LoCoMo：笔记 87% vs 原文 33% |

**代码默认值**：自然策略的 `termsFrom` 默认 `'recall'`；`gate` 默认值随本报告从 0 改为 0.3。Host 的 `snapshotDelivery` 仍默认 `append`（仅主 DSH 的部署未测 delta），用副本交付 View 时应设为 `delta`。

**什么时候不该用这套架构**：历史短到能整段放进上下文、而且同一段历史要被反复询问时（LoCoMo 每段约 2 万 token），直接全量放入更准也更便宜。副本架构的价值在于：记忆持续增长、事实会变化、上下文装不下或不该每次都读全部的场景（一周场景、4 倍语料、长工具任务）。

## 12. 局限

- 每个设置 1–2 次运行；长任务 1 次，噪声大（同一任务两次运行可差 20 个百分点，见上一轮报告）。
- 判分由 DeepSeek 完成，公开基准的绝对值不能与用 GPT-4o 判分的论文数字直接比较；基准只取了代表性子集（LoCoMo 3/10 段，LongMemEval 36/500 题）。
- 延迟的主要实验在高负载下测得（多个实验并行、交换区接近满），只有 §10 的复测是在低负载下。
- 本轮途中 TypeSafe（JEV）额度耗尽过一次，期间先跑了不需要 JEV 的基线与 BM25 对照；额度恢复后重跑了全部 JEV 组，报告中的 JEV 数据都来自恢复之后。
- 4 倍语料的实验里各组有 1–4 次服务端 520 或 JEV 超时，对应轮次沿用了旧 View。
