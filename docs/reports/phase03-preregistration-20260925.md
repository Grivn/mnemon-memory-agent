# 阶段 3 预登记：检索与答题的三项改进（gpt-4.1-mini）

日期：2026-09-25 · 分支：`codex/jev-replica-practice`（本地提交，不发布、不推送）

## 背景

gpt-4.1-mini 全集（mnemon (atlas)，线索召回 + 填满 8 条，原话写入）上，LongMemEval 跨会话题和时间推理题最弱，都只有约 69%。按"含答案的那一轮对话"逐条追踪答错的题，证据最早丢在哪一步：

| 题型（答错题数） | 检索没读到含答案的记录 | JEV 这一步丢失 | 证据全在 View 里仍答错 |
|---|---|---|---|
| 跨会话（39） | 24 | 8 | 7 |
| 时间推理（39） | 18 | 7 | 14 |

- 主要短板在检索：能找到证据所在的会话（95–97%），但找不到其中含答案的那一块。
- 候选池高度集中：69% 的名额落在"占了 4 块及以上"的会话里。
- 漏掉的含答案块中，约 1/5 紧挨着一块已读到的同会话记录。

## 改动

全部默认关闭，按开关启用。

1. **候选池按来源限额**（`poolPerGroup = 4`）：48 个候选名额里，同一来源（会话/文件/日期）最多先占 4 个，其他来源都轮到之后，剩余名额再按排名分。
2. **补入相邻记录**（`neighbors = 4`）：JEV 粗扫排名前 4 的条目，把它们前后相邻的记录（同一来源，按写入时间）放进精判名单的最后几位，最多占名单的 1/3。名单总长仍是 24，JEV 精判的条目数不变。
3. **汇总类问题多写检索词**（`gather = 5`）：回答需要凑齐多件事时（计数、合计、列举、比较、先后、间隔），线索规划写 4–5 条检索词，其他问题仍是 3 条。候选池仍是 48。
4. **时间题先列日期**（`--dates-first`，仅测评用的答题提示）：问日期、时长或先后时，先逐行列出相关事件及日期，再推算作答。

配套改动：记录类 Source 的检索路由每个 View 的调用上限从 8 提到 16。每次调用只是本地读取，不涉及模型。

## 实验安排

- **累加式三步**，每步都和上一步在同一批题上配对比较：
  - S1 = 改动 1 + 2；
  - S2 = S1 + 改动 3；
  - S3 = S2 + 改动 4；
  - 基线 S0 = 已有的全集运行（同一模型、同一流程）。
- **题目**：LongMemEval-S 全部 500 题；LoCoMo 开发集 150 题（每段对话前 15 题，以多跳、时间、开放域为主）。
- **模型**：答题和线索规划都用 gpt-4.1-mini，JEV 不变。
- **判分**：gpt-4.1-mini 为主，DeepSeek 为辅。
- **限流**：OpenAI 同时在途的请求不超过 6 个，每次只跑一个 OpenAI 任务。

## 指标

- **主要**：准确率（gpt-4.1-mini 判分）。看 LongMemEval 整体、跨会话 + 时间推理两类合计（260 题）、LoCoMo 开发集。
- **机制**：含答案的轮次进入 View 的比例；按题统计"含答案的轮次全部进入 View"的比例。
- **成本**：每题 JEV token 数和调用次数、每题总成本、延迟。

## 采纳标准（每一步对比上一步）

以下三条同时满足才采纳：

1. **有提升**：跨会话 + 时间推理合计提升 ≥ 3 个百分点，或 LongMemEval 整体提升 ≥ 1.5 个百分点。S3 看时间类题：LongMemEval 时间推理加 LoCoMo 时间题合计，提升 ≥ 3 个百分点。
2. **不退步**：LongMemEval 其余四类合计下降不超过 2 个百分点，LoCoMo 开发集下降不超过 3 个百分点。
3. **不加重 JEV**：每题 JEV token 数和调用次数，都不比上一步多出 10% 以上。

不满足的步骤不采纳，但照常报告机制指标。

**噪声参考**：同一配置跑两次，开发集上约 90% 的题判定相同，准确率相差 0–3 个百分点。

## 补充 5（2026-09-26 11:17，看过宽 View 重放、效用规则重放之前）

**背景。** JevAgent（S5h，DeepSeek 作答）在 LoCoMo 上错 160 题。

- **错题分布**：约一半是证据已全部进了 View 仍答错。另一半里，缺失的证据有 50% 从没进过候选池，42% 被 JEV 判过但没进 View。
- **JEV 自己的"把握"**：JEV 给出的最高分低于 0.5 的题占 20%，准确率 72.5%（其余题 93.9%），却包含了一半以上的错题。
- **宽 View 重放**：保持检索不变，只对这类题按 JEV 排序填到 16 条、不设分数下限，结果如下。

| 题集 | 改对 / 改错 | p |
|---|---|---|
| LoCoMo，最高分 < 0.5 | +21 / −7 | 0.013 |
| LoCoMo，保留 0.1 下限 | +6 / −5 | — |
| LoCoMo，最高分 ≥ 0.5 | +18 / −24 | — |
| LongMemEval，最高分 < 0.5 | +5 / −2 | — |

这条阶梯规则用的 0.5（JEV 的"需要 / 不需要"分界）和 16（View 上限）都不是在基准上挑出来的。但现行 View 规则里的入选线 0.4、填充 8 条、下限 0.1、同来源先取 2 条、汇总放宽 16 条，是 phase 1–2 看这两个基准的结果定的。用户要求用公式替代这些数，避免对基准过拟合。

**新增 S6a：效用规则（只改 View 的组装，检索和 JEV 判断不变）。**

- **规则**
  - JEV 判为需要的条目（needed ≥ 0.5，即 JEV 自己的是 / 否分界）先进入 View。
  - 其余条目按 JEV 的排序逐条考虑：
    - 单点需求：`s × R ≥ λ` 就加入。`R = Π(1 − s)` 是已展示的条目都不是所需证据的概率，在已展示条目上连乘。
    - 本题有"每个实例都要"的需求（ALL）：`s ≥ λ` 就加入，不乘 R。
  - 被取代的条目（superseded ≥ 0.6）仍不展示。上限 16 条、12,000 字不变，这是回答模型的预算。
  - 规划器没有列出任何需求时不填充，只展示 JEV 判为需要的条目。基准中不出现这种情况：规划器每题都至少列出一项需求。
  - 已在 View 中的条目（多轮对话）的保留规则不变，本评测不涉及。
- **替换掉的数**：对新条目的入选线 0.4、填充 8 条、填充下限 0.1、同来源先取 2 条、汇总需求放宽到 16 条（loopFill），以及阶梯规则的 0.5 门槛。
- **λ = 0.01，事先确定，不在基准上挑。**
  - 含义：新加的每一条，至少有 1% 的概率正好是缺的那条。等价于"为避免一次漏检，最多愿意多读 100 条"。
  - 依据：一条记录约 170 个回答模型 token，100 条约 17k token，与现在每题花在 JEV 上的 19–27k token 同一量级。也就是说，把答对一题的价值定为与现在每题愿意花在 JEV 上的量相当。
  - 另外报告 λ = 0.02 和 0.005 作为敏感度参照，不用于挑选。
  - 登记前看过的只有离线统计（View 条数、证据覆盖率），没有看过任何按此规则作答的准确率。
- **校准检查**（登记前做过）：JEV 的原始分数不做拟合校准，直接使用。
  - 在没把握的题里，原始分与实际命中率大致相当，例如排第 9 名的条目平均 0.11 分，实际 6% 是标准证据。
  - 在有把握的题里，低分偏高约 10 倍，但会被 R 压低。
  - 不需要记忆的对话由规划器的"无需求"处理，不在 LoCoMo 或 LongMemEval 上拟合校准表。
- **验证方式**：重放，做法与宽 View 重放相同。
  - 用 S5h 已记录的 JEV 判断，按新规则重组 View，DeepSeek 重新作答，DeepSeek 判分。
  - 与同样重放的原 View 逐题配对。原 View 在宽 View 重放中已有答案的题直接复用。
  - 范围：LoCoMo 全集和 LongMemEval 500 题中，View 被新规则改变的题。
- **采纳标准**（同时满足）
  1. LoCoMo 全集：与原 View 配对，净提升为正，且 McNemar p < 0.05。
  2. LongMemEval：与原 View 配对，整体不下降超过 0.5 个百分点。
  3. 不加重 JEV：检索和判断不变，JEV 的 token 数和调用次数不变。另外报告回答模型每题输入 token 的变化。
- **之后（S6b，另行登记）**：检索循环的阈值（覆盖 0.5、部分覆盖 0.3、进展 +0.05、前 4 个检索词、最多 3 轮、需求表 16 条且扫描分 ≥ 0.1）用同一框架替代。
  - 公式：这一轮还缺的概率 × 这一轮能补上的概率 ≥ 这一轮的代价 / 答对的价值。
  - 这一步需要 JEV 与回答模型 token 的价格比。暂按相同价格计，作为明示的假设。

## 补充 6（2026-09-26 11:45，S6a 效用规则重放结果出来之后）

**S6a（效用规则，λ = 0.01）不采纳。** 未满足采纳标准 1。以下为重放结果，与原 View 逐题配对。

| | LoCoMo | LongMemEval |
|---|---|---|
| λ = 0.01（登记值） | +26 / −30，净 −4，p = 0.69 | +10 / −8，净 +2 |
| λ = 0.005（敏感度参照） | +35 / −26，净 +9，p = 0.31 | +12 / −7，净 +5 |
| λ = 0.02（敏感度参照） | +28 / −21，净 +7，p = 0.39 | +7 / −14，净 −7 |

在 LoCoMo 上直接与阶梯规则比较（两者以同一批原 View 答案为基准）：效用规则 +20 / −38，净 −18，p = 0.025。

**原因。** 按 JEV 的把握拆开看：

| | 没把握的题（298） | 有把握的题 |
|---|---|---|
| 效用规则 | 平均 12.3 条，净 +3 | 加长了 411 题的 View，净 −5 |
| 阶梯规则 | 放宽到 16 条，净 +14 | 不改动 |

登记前的校准检查只看了没把握的题（原始分与命中率相当），漏看了有把握的题：那里 JEV 的低分偏高约 10 倍，R 也被高估。公式因此在有把握的题里加进噪声，在没把握的题里又收得过早。

**结论：** JEV 的分数没有校准时，不能把它当概率连乘。阶梯规则只用 JEV 的是 / 否分界（0.5）、它的排序和 View 上限（16），都是序数信号或预算约束，没有在基准上挑出来的数，所以更稳。

**阶梯规则采纳，实现为 `unsureFill`。** JEV 对所有候选都判"不需要"（没有任何未被取代的条目达到 0.5）时，按 JEV 的排序填到这么多条，不设分数下限；其余情况 View 规则不变。依据是宽 View 重放：

- LoCoMo：+21 / −7，p = 0.013，折合全集 +0.9；
- LongMemEval：+5 / −2，没有退步；
- 有把握的题不改动，因为放宽对它们没有收益（+18 / −24）。

**新增 S6c：校准后的效用规则（重放，登记于看到任何 S6c 结果之前）。** 这一步检验：把 JEV 的分数校准之后，公式能否达到或超过阶梯规则。

- **校准模型**：P(标准证据 | s, s_max)，对 logit(s) 和 logit(本题最高分) 做逻辑回归，共 3 个参数。本题最高分用来表达"同一个分数在有把握和没把握的题里含义不同"。
- **交叉拟合，避免在被检验的数据上拟合**：在 LongMemEval 上拟合、用于 LoCoMo；在 LoCoMo 上拟合、用于 LongMemEval。
- **规则**：与 S6a 相同，只是 s 和 R 都换成校准后的概率。λ = 0.01 不变。
- **采纳标准**：与阶梯规则在同一基准上直接比较。LoCoMo 净提升为正且 p < 0.05，同时 LongMemEval 不差于阶梯规则，才替代阶梯规则。两者相当时保留阶梯规则，因为它更简单，也不需要维护校准模型。
- **检索循环的公式化（原 S6b）推迟。** 它同样依赖"证据还缺的概率"：未校准时，十几条 0.05 分的无关条目连乘，会让这个概率从 1 掉到 0.44 左右。等 S6c 证明校准可行之后再登记。

## 补充 10（2026-09-26 18:20，简洁模式，实现和运行之前）

**目的。** View 规则和 JevAgent 循环里还有十几个经验手定的数和规则。这一步把它们换成三类有明确含义的依据：

- JEV 的是 / 否判断，0.5 是它自己的分界线；
- JEV 的排序，加上系统预算；
- 上一步观察到的事件。

检验去掉这些数之后，准确率是否不比 S6 差，成本是否可以接受。

**预算**（人定，含义明确，本步不变）：

- 规划模型至多列 3 个需求；
- 每次检索读一页，20 条 / 12,000 字；
- 首轮候选池 48 条，作为 JEV 的筛选预算。这个数当初按 LoCoMo 离线覆盖率定，本步不改动；
- 循环至多 3 轮；
- View 16 条 / 12,000 字。

**简洁模式的规则**（开关 `--simple`，配置 `simple`，默认关闭）：

1. **View**
   - JEV 细判为"需要"（≥ 0.5）的条目进入 View。
   - 规划模型列出了需求（这一轮需要记忆）时，再按 JEV 细判的排序补满 View 预算，不设分数下限，也不限同一来源的条数。规划模型没有列出需求时，只放判"需要"的条目。
   - JEV 判为"已过时"（≥ 0.5）的条目不展示；已在 View 中的撤下。
   - 已在 View 中的条目（多轮对话）与新条目同样处理：仍判"需要"或按排序仍在预算内，就保留。
2. **只判可能进 View 的条目**
   - 细判：已在 View 中的条目、需求表里判"是"的全部条目、筛选判"需要"的条目，以及筛选排序前 16 条（View 预算）。
   - 需求表：每轮新读到的条目中，筛选判"需要"的，加上筛选排序前 16 条。只有一个单点需求时，与现在相同，用筛选结果代替需求表。
   - JEV 每次调用的条数上限（细判 40 条、需求表 24 条）和细判总数上限 64 条，是调用大小的限制，不变。
3. **循环**：每个需求每轮至多一个动作。
   - 单点需求：需求表里已有"是"，就算满足。
   - 汇总需求：规划模型标为 ALL，或需求表里已有至少 2 条不同记录对它判"是"。
     - 上一轮出现了新的"是"：沿发现这些新"是"的检索各翻一页。第一轮时，首轮检索找到的"是"都算新的。
     - 没有新的"是"，或这些检索都没有下一页：结束。
   - 还没有"是"的需求（单点或汇总）：
     - 线索是需求表里对它排第一的记录。线索所在的检索，是把这条记录排得最靠前的那条检索。
     - 上一步翻页后没有改进：换说法，由规划模型写一条新检索，读一页。
     - 否则，线索所在的检索还有下一页就翻页，没有就换说法。
     - 翻页和换说法都做过，且都没有改进：放弃。
     - "改进"指出现了新的"是"，或排第一的线索换成了这一轮新读到的记录。
   - 所有需求都已满足、结束或放弃，或 3 轮用完，就停止。
   - 没有规划模型时（快速模式），不能换说法，翻页没有改进就放弃。快速模式不在本步的验证范围内。
4. **不变的部分**：规划模型的两次调用（检索词、需求）及其提示词，混合检索与融合，JEV 筛选和细判的问题，回答模型。

**实现（提交 5aeea37a）：**
1. **提前算好概括文本的向量（插件改动，只影响速度）。**
   - 做法：后台任务整合到没有新记录可读时（对话暂停），先把 View 要按语义排序的文本算好向量，即每个话题的时间线摘要和每个值的历史。View 的排序和内容都不变。
   - 起因：冒烟测试中，LongMemEval-S 的一段历史整合出 138 个话题、129 个值。第一个 View 要现算这 267 条的向量，本地向量服务每秒约 25 条，View 超过了 30 秒的等待上限，这题在没有记忆的情况下作答。修复后，同一题的 View 7.5 秒就送达了。
2. **HaluMem 按用户增量写入（测评框架改动，`--incremental`）。**
   - 原因：HaluMem 中每个挂题的会话单独成一个案例，案例的历史是该用户到这个会话为止的全部会话（20 位用户，共 896 个案例）。若每个案例都从头整合，要读约 3 亿字符（约 3 万批，估计 $85），也不符合实际使用。按用户增量整合，每位用户的历史只整合一次（约 1,350 批）。
   - 做法：
     - 同一位用户的案例按会话数从少到多依次运行，共用一个 journal；
     - 每个案例只写入它新增的会话（中位 1 个，最多 5 个）；
     - 整合状态接着上一个案例继续。
   - 与登记运行一致的地方：
     - 每个案例仍然新起工作进程，账本和通道也是新的（上一个案例的 main、replica、transport 目录移到 `cases/<id>` 保存）；
     - 每道题有自己的会话 id；
     - journal 中记录的内容和顺序与登记运行相同，只有记录 id 和创建时间不同。
   - 唯一从上一个案例延续下来的，是 journal 和整合状态。
   - 已检查全部 896 个案例：每个都是同一用户前一个案例的延伸。
3. **预热到追上为止。**
   - 开启整合时，预热的后台任务一直跑到某次任务既没有新记录可读、也没有剩下待整合的记录为止，上限为 `--warm 20`。
